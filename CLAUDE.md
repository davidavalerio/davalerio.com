# davalerio.com

## What This Is

Personal calling card for David Valerio, map-led, plus his writing. The homepage opens on a single screen: a line drawing of the Missouri and the Yellowstone at Williston, seen from above, with a card (headshot, name, tagline, and links to Writing, Maps, Podcasts and email) set over the city; this is the URL David hands out at presentations and on business cards. Below it, on the same page, are three columns: Writing (essays and papers), Maps and Podcasts (the Discern Earth conversations), each newest first. Each piece has its own page at `/writing/<slug>/`; there is no separate Writing index (`/writing/` forwards to the homepage's `#writing` section).

This is a personal site, not a services site. Don't propose services sections, contact forms, pricing, or training-related copy for it; "update the homepage" means extending the personal page.

There is no consulting page: the former AI consulting page is removed and survives only in git history.

## Stack

Static HTML. Source Serif 4 via Google Fonts. The homepage is hand-made with inline CSS and no JavaScript; only the writing list inside it is generated. The writing section and the map pages are generated by `_writing/build.py` (Python, PyYAML, Pandoc; run it as `uv run --no-project --with pyyaml python3 _writing/build.py`) and the generated pages are committed, so GitHub Pages serves plain files. Only pages that carry a map load JavaScript (Maps, below).

## Publishing a Piece

Essays are drafted in the Strata vault (`3_Write/Essays/`). To publish one: copy the note to `_writing/posts/<slug>.md`, keep `title`, `subtitle`, and `date` in the frontmatter and add `kind` (defaults to essay), copy any image the note shows into `writing/files/` and point its link at `/writing/files/<name>`, run `_writing/build.py`, then `/deploy`. A map piece is drafted in `_writing/drafts/` first and read on the local server (Maps, below). Publishing sends no email; a piece goes to subscribers only when David asks for it (Writing by Email, below). Readers can also follow `/writing/feed.xml`.

**Images on pieces are David's own work only.** Maps, figures, renders and photos David made himself may appear on a piece, including maps built from public-domain data (USGS, NDGS, Census) or other data whose license allows publishing, credited in the caption. Nothing made by anyone else goes on a piece (no stock or borrowed photos, no header images from elsewhere), so there is no image-rights exposure; strip any that come in with a draft. Embedded podcast players and linked PDFs of David's own papers are fine.

## Maps

Maps appear three ways: as passages of an essay that turn one pinned map to named views, as a map set into an essay that readers explore, and as a map page of its own at `/maps/<name>/` when its definition says `page: true`. The homepage's Maps column is hand-made, and every map in it is native to the site (an interactive map or a turnable model), never a PDF: The Missouri and the Yellowstone (`missouri-yellowstone`, the line drawing from the Williston Confluence project in Drive), The Basin, Exploded, the Geologic Map of Western North Dakota (`western-nd-geology`) and Byzantine Catholic Parishes (`byzantine-parishes`), each built from its Drive project by the tile script beside its definition. Williston and the Missouri keeps its page but is not listed. The maps follow the Practice Design System: the page frame in Source Serif, everything on the map itself (labels, popups, the key) in Source Sans 3, which `map_head` loads. A map page can also hold a print map instead, shown as its image (`image` and `alt` in the definition, the file copied into `maps/<name>/`), with a link to its PDF when the definition names one (`pdf`). Such a page can be a turnable model of the print instead (`model: <folder>`, with `build:` naming its Drive build folder under `1-Practice/GIS/`): a stack of sheets drawn by `maps/model.js` from the files in `maps/<name>/<folder>/` (`model.json`, and a `.bin` and a `.jpg` per sheet), which readers turn and zoom, with a slider from the print's even spacing to each sheet's true depth, the layer names on the sheets and a key beneath. A model is the main form of such a piece on the site and carries no PDF link; the image and PDF go out for distribution from Drive, and the image stays on the page, unseen, for print and for browsers without JavaScript or WebGL 2. The Basin, Exploded is one: its Drive build (`Basin Exploded/Scripts/build.sh`) reads its shape, light, colours and camera from `settings.json` beside it and writes the PNG, the PDF and the model's files (its `Web/` folder, format in `web.py`); when it changes, the PNG and `Web/`'s `.bin`, `.jpg` and `model.json` files are copied here (its `-field.png` files are for the workbench only).

**Workbench.** `_writing/workbench/` is a private page for tuning every 3D piece live and saving what works back where the piece is made. It runs only when asked for, from the repo root on the mini: `node _writing/workbench/workbench.mjs` serves it on 127.0.0.1:8795, and while it runs Tailscale publishes it at port 8796 of the mini's tailnet name, which only David's devices reach (the tailnet's rules keep shared users to port 443); it is opened on the laptop with `laptop.sh url`. It lists every map definition with something to tune and builds its panel from the settings each piece declares, as a list of `{key, label, group, type, value}` with type number (`min`, `max`, `step`), color or view. A model declares them in its Drive build's `settings.json`, shown from the build's `Web/` folder and saved back into that file, which the next rebuild uses. A terrain map's settings come from its definition (terrain exaggeration and its named views, framed for 1200 × 800 whatever the workbench's map size) and from the `--map-…` palette in `maps/map.css` that its layers use, light and dark; saving writes those files and rebuilds the map pages, and the stills are captured again before such a change is deployed. Show and hide switches are for looking only. A new kind of piece joins with its declaration and an adapter in `workbench.js` that draws it and applies a setting. The Drive folder holding the builds is read from `~/.local/share/workbench/config.json`.

**Key and popups.** A definition's `legend` (groups, each an optional `heading` and `items` of `label`, `color` as a hex or `--map-…` token, optional `code`, and `shape` fill, dot or line with `dash` dashed or dotted) is drawn as a key beneath a map page's map, and its `popup` (`layer`, `title` and `lines`, each a template of `{field}` names; an empty line is dropped) shows a feature's details when it is clicked, on map pages and embeds only.

**Definition.** `_writing/maps/<name>.yaml` holds the title, date and note for its page (the note describes the map; how to move it goes in `hint`, shown after the note on the page and left out of email), the credits (data sources only: no AI model or tool is credited on anything published), `bounds` the map can be moved within, the terrain `exaggeration`, the tile `sources`, the MapLibre `layers` (colors written as `--map-…` tokens from `maps/map.css`, so they follow light and dark mode), `labels` (placed as page text in Source Serif, so the maps need no font files), and named `views`: each a camera (`center`, `zoom`, `pitch`, `bearing`), whether terrain is on, the layers and labels it `show`s, and the still's `alt` and `caption`. Views are framed for a 1200 × 800 map; smaller maps zoom out a little to keep about the same ground in view. The maps carry only David's own layers, with no basemap.

**Tiles.** A map's data is built on the mini by its script, run with QGIS's Python as its header says; it reads the project in Drive without touching it, works in a scratch folder, and writes `vectors.pmtiles` (from the GeoPackage, through GDAL) and `terrain.pmtiles` (Terrarium-encoded elevation in quarter-meter steps, the project's DEM faded into a coarser 3DEP download around it so tilted views have land past the project's edge) into `maps/<name>/`. It needs the `pmtiles` command (Homebrew). Tiles are served from the site; a map whose files outgrow GitHub's limits (100 MB a file) would move them to Cloudflare R2, which no map has needed.

**Stills.** Every view has a still image, `maps/<name>/stills/<view>.jpg`, captured from the map's own page by `node _writing/stills.mjs <name>` (headless Chrome through playwright-core in `~/.local/share/site-stills`). The stills are what a reader sees in email, the feed, print and without JavaScript, and they stay on screen until the live map has drawn; they are captured again whenever a map's data or views change, before `build.py`. A published piece fails to build if a still is missing.

**Writing a map piece.** The piece's frontmatter names its map (`map: <name>`), and David marks passages in plain markdown:

    ::: {.map-step view=contours}
    The passage that goes with this view.
    :::

    ::: {.map-embed view=relief}
    Caption for a map readers can explore.
    :::

A caption's instruction for moving the map is marked `[...]{.live}`: it shows only once the map can be moved, and the feed and email leave it out. Consecutive steps share one map, pinned beside the text on desktop and above it on phones, with an Explore Map / Return to Story button that opens it full screen to pan, zoom and tilt. Each change of view gets its still (linking to its passage) and an anchor, `#view-<name>`. A note at the top, shown only in email and the feed, points readers to the site. The first still is the piece's share image.

## Brand Identity

**Name:** "David Valerio" is the canonical name. No middle initial.

**Favicon:** the initials DV in Source Serif bold, muted plum (`#5E4B8B`), on a clear background, drawn as outlines inline in `index.html` (source in `_writing/favicon.txt`; the drawing switches itself to the dark-mode accent in a dark browser). `favicon.png` is the same mark as a transparent 64px fallback for Safari, rendered from the drawing with headless Chrome (`--default-background-color=00000000`). `apple-touch-icon.png` keeps the mark on the paper color, because iOS paints transparent areas black.

## Design System

The site follows the Practice Design System, David's house style shared with his documents and utility emails and separate from the Discern Earth brand. Its live version is the Design System artifact of that name (read it fresh when the site's look is in question): Source Serif 4 alone (regular text, semibold name and headings), slate ink (`--ink`), stone gray for the tagline and metadata (`--stone`), barely warm paper (`--paper`), and one muted-plum accent (`--accent`, `#5E4B8B`) on the links, which carry no underline and turn ink on hover. Circular headshot with a hairline border, the one round shape on the site; everything else has square corners. Nothing on the site is set in all caps: metadata lines (kind and date above a piece, the dates in the list) are stone at 0.78rem with 0.02em tracking in normal case, and dates are written `YYYY-MM-DD`.

The writing pages use the same tokens in `writing/style.css`: a 41rem measure and the site's own reading scale (the system's 15px screen scale is sized for emails), a hairline masthead (name left, Writing right), italic stone subtitles, and a print stylesheet.

**Dark mode** follows the device setting, with no toggle: a `prefers-color-scheme: dark` block (screen only, so print stays light) swaps the token values in both `index.html` and `writing/style.css` — paper `#16191B`, ink `#E4E0D8`, stone `#9BA0A4`, hairline `#32383C`, accent `#A08CD0` (plum lightened to stay readable), block quotes `#C2C0BA`. Keep every color on a token so both modes stay in step; the two files' values must match.

## Layout

The first screen (`.card-screen`) is the line drawing as a still image filling the screen from its top edge, with the card set over Williston: a bordered paper panel, centered, holding the portrait, name, tagline and Writing, Maps, Podcasts and Email. The drawing is centered on Williston, reaching equally far in every direction and west past the Yellowstone's confluence, and it fades into the paper on every side. The image's 150-pixel strip of paper sits above the screen, and the card is sized and placed in the image's own pixels (`--px`) over the city's spot in it (785, 555 of 1600 × 1000), so the card stays on Williston at any window size. The drawing never shows larger than the map's own page shows it (zoom 9.29, `--px` 0.894): on a larger window it stays at that scale, centered in paper. The first screen is always the drawing's full height, so the card never runs into the columns below. The first screen carries no caption; the map's own page names it and its sources. On tall or narrow screens (a phone either way up, a portrait tablet, any window under 900 pixels wide) the whole drawing comes first and the card rises onto its lower edge, and the first screen ends there rather than filling the screen. Below the first screen, a 76rem grid of three equal columns: Writing (the seven newest essays and papers, the rest behind All Writing), Maps (three maps, each a row with its title and date and its snapshot to the right, the rest behind All Maps) and Podcasts (the seven newest episodes, the rest behind All Podcasts: the Discern Earth conversations, listed by the guest's name and linked to their pages, and David's guest appearances on other shows from `_writing/appearances.yaml`, listed by the show's name and linked to the episode on Apple Podcasts). The three columns share their rows through a subgrid, so each column's entries spread to begin and end at the same depth as the others'. The toggles are plain `<details>`, so the page needs no script; the headings carry no counts, and no column labels its items by kind. The columns stack on phones in the same order, Writing first. Below them, across the grid's width under a hairline, sits the centered Writing by Email band. To recapture the drawing behind the card, rebuild the Williston Confluence project in Drive and the map's tiles, then capture the four `home/hero-*.jpg` images from the map at the card's view (desktop 1600 × 1000 at twice the pixel density, north up and flat, the drawing below a 150-pixel strip of paper, kept above the screen; tall screens 860 × 600 with the whole drawing), without labels.

## Writing by Email

Readers subscribe with the Writing by Email box, a band below the homepage's three columns and at the foot of every essay, paper and map page (`SUBSCRIBE` in `build.py`; the homepage's copy and its styles are hand-made in `index.html`, kept in step with `writing/style.css`). The form posts to a Cloudflare Worker at subscribe.davalerio.com (`_subscribe/worker.js`), which turns away anything filling the hidden `website` field and caps confirmation mail at a few a minute per sender and per address, one per address a day (a repeat lands on the same page, sending nothing) and 50 a day in all. It emails a link whose token carries the address and the time encrypted, so the address never shows in the link, and sends the reader to `/subscribe/sent/`. The link expires after seven days and works once: it opens a Confirm Subscription button, and only that click adds the address to the Writing segment in Resend and lands on `/subscribe/confirmed/` once Resend shows them in it; pressed again, it says Link Already Used and changes nothing, so an old email cannot undo a later unsubscribe. A link is claimed before Resend is touched and released only when nothing changed; when Resend may have taken the change without confirming it, pressing the link again only checks the contact. A confirmation email whose send was uncertain is retried on the reader's next request as the identical email under the same idempotency key, so Resend delivers it at most once. Resend's unsubscribe covers the whole account, so the click subscribes again someone who once unsubscribed only when Writing is their only segment; anyone in another segment keeps the opt-out and is told to write to david@. Nothing is added to Resend before the click. The caps and used links live in the Worker's Ledger, a Durable Object whose calls run one at a time so simultaneous requests cannot slip past them; it holds only fingerprints (of addresses for a day, of used links until they expire) and a count per day, and the Worker never logs addresses, though the confirmation email itself passes through Resend, which keeps its own logs. The Worker is deployed by hand from `_subscribe/` with `npx wrangler deploy`, under wrangler's own Cloudflare sign-in on the mini (`wrangler login --device`, limited to Workers and read access; run it again if the sign-in lapses); its secrets are `RESEND_API_KEY`, `SEGMENT_ID` and `SIGNING_KEY` (changing `SIGNING_KEY` voids unconfirmed links).

Nothing is emailed on publish. David asks for a piece by its slug or a map page by its name, and the newsletter workflow sends it, run from its Run button on GitHub or with `gh workflow run newsletter.yml -f name=<name> -f to=test`: `to=test` (the default) mails David alone, and only a second run with `to=subscribers` mails the list as a Resend broadcast named `writing:<slug>` or `map:<name>`. An essay or paper goes as its full text, with a map piece's stills linking to their views, captions without their `[...]{.live}` hints and the credits once at the end (`offline()` in `build.py`, which the feed uses too); a map page goes as its title, opening still, note, a link to explore it and its credits; conversations are not emailed. Everything is from David Valerio at writing@davalerio.com with replies to david@, ending in Read on davalerio.com · Unsubscribe and a line saying the reader subscribed at davalerio.com (Resend handles unsubscribes; no postal address, by David's choice). The subscriber send runs only in the workflow on main, after a successful test of the same piece on the same commit, and only when the live page is byte for byte the page that commit's source renders, so an unpublished edit, or a source edit never rebuilt, is never mailed. A name Resend lists as already sent never goes again; one Resend shows as stopped partway, in any status but draft, or as a draft from the last ten minutes stops the run for a look in Resend; a failed or uncertain send stops and says so, and is checked in Resend before running again. `send.py <name> --preview` prints the email. The repo's secrets `RESEND_API_KEY` and `SEGMENT_ID` feed the workflow.
