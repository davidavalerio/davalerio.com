# davalerio.com

## What This Is

Personal calling card for David Valerio, map-led, plus his writing. The homepage opens on a single screen: a line drawing of the Missouri and the Yellowstone at Williston, seen from above, with a card (headshot, name, tagline, and links to Writing, Maps, Podcasts, Subscribe and email) set over the city; this is the URL David hands out at presentations and on business cards. Below it, on the same page, are three lists, one beneath the other: Writing (essays and papers), Maps and Podcasts (the Discern Earth conversations), each newest first. Each piece has its own page at `/writing/<slug>/`; there is no separate Writing index (`/writing/` forwards to the homepage's `#writing` section).

This is a personal site, not a services site. Don't propose services sections, contact forms, pricing, or training-related copy for it; "update the homepage" means extending the personal page.

There is no consulting page: the former AI consulting page is removed and survives only in git history.

## Stack

Static HTML. Source Serif 4 via Google Fonts. The homepage is hand-made with inline CSS and no JavaScript; only the writing list inside it is generated. The writing section and the map pages are generated by `_writing/build.py` (Python, PyYAML, Pandoc; run it as `uv run --no-project --with pyyaml python3 _writing/build.py`) and the generated pages are committed, so GitHub Pages serves plain files. Every generated page links `writing/style.css`, `maps/map.css`, `maps/map.js` and `maps/model.js` with a mark taken from the file's contents (`asset()` in `build.py`), so a browser fetches a changed file at once instead of keeping its copy for GitHub Pages' 10 minutes; after editing any of those four, `build.py` runs before deploying so the pages carry the new mark. Only pages that carry a map load JavaScript (Maps, below).

## Publishing a Piece

Essays are drafted in the Strata vault (`3_Write/Essays/`). To publish one: copy the note to `_writing/posts/<slug>.md`, keep `title`, `subtitle`, and `date` in the frontmatter and add `kind` (defaults to essay), copy any image the note shows into `writing/files/` and point its link at `/writing/files/<name>`, run `_writing/build.py`, then `/deploy`. A map piece is drafted in `_writing/drafts/` first and read on the local server (Maps, below). Publishing sends no email; a piece goes to subscribers only when David asks for it (Writing by Email, below). Readers can also follow `/writing/feed.xml`.

**Images on pieces are David's own work only.** Maps, figures, renders and photos David made himself may appear on a piece, including maps built from public-domain data (USGS, NDGS, Census) or other data whose license allows publishing, credited in the caption. Nothing made by anyone else goes on a piece (no stock or borrowed photos, no header images from elsewhere), so there is no image-rights exposure; strip any that come in with a draft. Embedded podcast players and linked PDFs of David's own papers are fine.

## Maps

Maps appear three ways: as passages of an essay that turn one pinned map to named views, as a map set into an essay that readers explore, and as a map page of its own at `/maps/<name>/` when its definition says `page: true`. The homepage's Maps list is hand-made, and every map in it is native to the site (an interactive map or a turnable model), never a PDF: The Missouri and the Yellowstone (`missouri-yellowstone`, the line drawing from the Williston Confluence project in Drive), The Williston Basin, Exposed, the Geologic Map of Western North Dakota (`western-nd-geology`) and Byzantine Catholic Parishes (`byzantine-parishes`), each built from its Drive project by the tile script beside its definition. Williston and the Missouri keeps its page but is not listed. Every map and model readers can move (a map page's map, an embed, an essay's pinned map, a turnable model) sits inside a 1px frame in `--frame` (`maps/map.css`), a shade darker than the hairline, so the edge of what moves is plain to see; still images keep the hairline. The maps follow the Practice Design System: the page frame in Source Serif, everything on the map itself (labels, popups, the key) in Source Sans 3, which `map_head` preloads from `fonts/`. A map page can also hold a print map instead, shown as its image (`image` and `alt` in the definition, the file copied into `maps/<name>/`), with a link to its PDF when the definition names one (`pdf`). Such a page can be a turnable model of the print instead (`model: <folder>`, with `build:` naming its Drive build folder under `1-Practice/GIS/`): a stack of sheets drawn by `maps/model.js` from the files in `maps/<name>/<folder>/` (`model.json`, and a `.bin` and a `.jpg` per sheet), which readers turn and zoom, with a slider from the print's even spacing to each sheet's true depth, the layer names on the sheets and a key beneath. A model is the main form of such a piece on the site and carries no PDF link; the image and PDF go out for distribution from Drive, and the image stays on the page, unseen, for print and for browsers without JavaScript or WebGL 2. The Williston Basin, Exposed is one: its Drive build (`Basin Exploded/Scripts/build.sh`) reads its shape, light, colours and camera from `settings.json` beside it and writes the PNG, the PDF and the model's files (its `Web/` folder, format in `web.py`); when it changes, the PNG and `Web/`'s `.bin`, `.jpg` and `model.json` files are copied here (its `-field.png` files are for the workbench only).

**Workbench.** `_writing/workbench/` is a private page for tuning every map live and editing its page's text, saving what works back where the piece is made. It runs only when asked for, from the repo root on the mini: `node _writing/workbench/workbench.mjs` serves it on 127.0.0.1:8795, and while it runs Tailscale publishes it at port 8796 of the mini's tailnet name, which only David's devices reach (the tailnet's rules keep shared users to port 443); it is opened on the laptop with `laptop.sh url`. It is in the house style, light only, like the site. It lists every map definition and builds its panel from the settings each piece declares, as a list of `{key, label, group, type, value}` with type number (`min`, `max`, `step`), color, view or text. Every map shows its title and note above it and its credits below, laid out as on its page, and David edits those in place by clicking into them (a new title also goes into the map's entry in the homepage's Maps list); the legend beneath the map is edited there too, whole: headings and labels retyped, a swatch's shape and colour (a map token or any colour) changed, and items and groups moved (dragged by a group's heading or an item's row, or with the small arrows), added and removed, saved into the definition's `legend`; the box showing the markdown while he types (Command-K makes the selected words a link, the cursor left where the address goes) and the text as the page will show it once he clicks away; saving writes them into the definition and rebuilds the map pages. A print page with neither views nor a model shows its image, with only its text to edit. A model declares them in its Drive build's `settings.json`, shown from the build's `Web/` folder and saved back into that file, which the next rebuild uses. An interactive map's settings come from its definition (terrain exaggeration when it has terrain, and its named views, framed for 1200 × 800 whatever the workbench's map size) and from the `--map-…` palette in `maps/map.css` that its layers use; saving writes those files and rebuilds the map pages, and the stills are captured again before such a change is deployed. Show and hide switches are for looking only. A map with a print form (a print map that follows it, under **Print maps**) has one entry in the list, with a Web and Print switch beside it; saving the web map rebuilds that print map's PDF, and saving the palette rebuilds every print map that follows a web map. A new kind of piece joins with its declaration and an adapter in `workbench.js` that draws it and applies a setting. The Drive folder holding the builds is read from `~/.local/share/workbench/config.json`. David's saves land in the working tree uncommitted, so a session's own commit stages only the files its change touched, never everything, and his saved edits ship only when he says.

**Key and popups.** A definition's `legend` (groups, each an optional `heading` and `items` of `label`, `color` as a hex or `--map-…` token, optional `code`, and `shape` fill, dot or line with `dash` dashed or dotted) is drawn as a key beneath a map page's map, and its `popup` (`layer`, `title` and `lines`, each a template of `{field}` names; an empty line is dropped) shows a feature's details when it is clicked, on map pages and embeds only.

**Print maps.** A print map is built from code by the engine in `_writing/print/`, with no QGIS. Each map lives in its Drive GIS project: `Scripts/map.py` says what the map is (its pages, frames, layers, label rules, and every tunable setting with its default), `Scripts/settings.json` holds the saved values, in the same `{key, label, group, type, value}` shape as a model's, and `Scripts/data.py`, where the data was pulled, rebuilds the project's GeoPackage and rasters from the downloaded products with each layer's citation in its description. The print maps are Williston Area (letter), the Geologic Map of Western North Dakota (tabloid; frame at the left, a two-column legend, a locator and two scale bars beside it), Byzantine-Rite Catholic Parishes of the United States (two letter pages in Albers, Alaska and Hawaii in frames of their own) and The Williston Basin, Exposed (portrait tabloid: its Blender render as a picture, from the project's `Render/` folder, with its names and figures as labels on it; its print settings are the `print.…` entries of the same `settings.json` its model uses). Each is the print form of a web map, named in its map.py (`WEB = '<name>'`): the web map is its source of truth. A setting declared with a value from `web` (`web.title`, `web.credits(tail)`, `web.legend`, `web.paint(layer, key)`, `web.token(name)`) takes the web map's value, palette tokens as written and the paper white, and follows it; `settings.json` holds such a setting only while print holds it to another value, and the workbench panel lists each such change with a button that returns it to the web value. Every layer of the web map has a print switch (`layer.<id>`, under Layers), and map.py draws each by asking `m.layer('<id>')`; a web layer it never asks about stops the build, and a layer switched off takes with it the legend items whose colour no drawn web layer still uses. Line weights, dot and type sizes, extents, pages, label pins and what the web map has no notion of (a relief's tints, a marsh) are print's own. A page left alone takes the standard layout (title block above one frame; scale bar, credits and north arrow beneath, the footer as tall as the credits need and the frame taking the rest; a legend column when the map has a legend); a map with its own arrangement gives each frame its rectangle and projection and says where each piece goes (`place`). A frame can also hold a picture in place of ground (`Page.image`, for a Blender render), its lettering given as labels in the picture's own 0-to-1 positions. `uv run build.py "<project folder>"` (run in `_writing/print/`) writes each page as one static HTML document sized in inches with its map as inline SVG, prints it in the pinned Chromium, checks the PDF (every font embedded TrueType, every title, credit and label found as text, the relief at 350 dpi, the page size), and draws the PNG from the PDF with poppler (one per page for a map of several pages, `…-Page-1.png`); `--move` then puts `YYYY-MM-DD-Name-Map.pdf` and `.png` into the project (a map names its files otherwise with `OUTPUT`), and only a build that passed is moved. Python does the geography: layers are read from GeoPackages opened read-only and immutable, relief is shaded and tinted from the elevation raster, and labels are placed by one deterministic engine (`labels.py`: a name beside a point, inside an area, along a line, a figure on a contour with the line cut beneath it, never a halo; lines a rule names are cut under its labels, and a label takes the place with the least linework beneath it). The credits' `{sources}` is filled from each drawn layer's citation, the first line of its GeoPackage description (a raster's image description), and a drawn layer with no citation stops the build, whether or not the credits print the sources. Label positions David has dragged are pins in the `labels` setting, stored as ground (a point label's offset from its symbol in points; an area or free label's longitude and latitude; a line label's distance along its line), so they hold when the extent or the page size changes. `proof.py` reprints the proof page that shows what Chromium writes into a PDF, for after a Playwright bump, and `test_print.py` tests the engine on a made-up map. In the workbench every project in the Drive GIS folder with both files is a print map, reached by the Print switch on its web map's entry (one that follows no web map is listed under Print Maps): opening one starts a Python session (`session.py`) for that browser tab, which the server keeps and speaks to over its pipes (stopped when the tab closes, reloads or turns to another piece, or after two minutes unheard from, with no more than four running at once; a tab whose session has gone opens another with its unsaved changes at its next change). One tab edits a print map at a time: the first to open it is its editor, and another tab opening it meanwhile is view-only, with a notice and a Take Over button; taking over makes the first tab view-only within ten seconds, with a notice, and its unsaved changes are discarded. Being the editor belongs to the tab, not to its session: it ends when the tab closes, reloads or leaves the map, after two minutes unheard from, or at a take-over, and a session stopped to make room for others does not end it. Every preview the session builds is numbered, and every change of settings, label edit, extent change and page fetch names the preview it was made on: one made on a preview since replaced is not acted on, and the page redraws from the current one, so a label edit can never land on a label other than the one that was seen. The page shows in a frame scaled to fit (a map of several pages has a page switcher, and each page's pins are its own), and it is tuned there: colours, weights, opacity and an unlabelled layer's switch change the page at once; everything else is redrawn by the session, which sends back only the pieces that changed. On the page itself the title, subtitle and credits are typed in place, the frame is dragged (and pinched, or the wheel turned with Control or Command) to change its extent, and labels are dragged (a name on a line slides along it, and comes free of it when pulled well away), deleted with Delete, reset to automatic with a double-click (that label alone), and reworded with Return (Shift-Return for a line break); a legend is edited beneath the page as a web map's is, its colours hex or the key of a colour setting. Beneath the page the workbench names labels left off (a switch shows them faintly, to be dragged in), pins waiting outside the frame, and pins whose feature has left the data. A drag is an edit made on the preview it began on, so one the page was redrawn under is not applied. Save shuts the page, panel, text and the Save, Revert and map controls from the click until its answer is applied, waits for any change still being drawn (and stops, saving nothing, if one of them is refused, or while any setting holds a value the page could not be drawn with), writes the editor's changed values into `settings.json` (a new file beside it, renamed over it, so a failed write leaves the old one whole) and rebuilds the PDF in the background; nothing is merged, and if the file has changed on disk since the map was opened (another workbench, a hand edit) the save is refused with a message and an offer to read the map again from disk. After a save the status line says when the PDF is in the project or why it was not rebuilt (the last PDF then stands). One build of a project runs at a time, from the workbench or the command line, each in a working folder of its own; a second waits for the first. A map whose saved settings hold a value the page cannot be drawn with still opens, with that setting at its default and a message naming it, and the next save replaces it. A label's text box, like a drag, belongs to the preview it was opened on: if the page was redrawn meanwhile the new wording is refused and the page shown as it stands. `WORKBENCH_PORT` and `WORKBENCH_GIS` run a second workbench on another port against another GIS folder, for testing.

**Definition.** `_writing/maps/<name>.yaml` holds the title, date and note for its page (the note and the credits are markdown: each new line is a line break, a blank line starts a paragraph, lines starting "- " make a list, and `[text](url)` or a full web address (`https://…`) makes a link, which is how a data source is linked; the note describes the map; no map page, caption or email tells readers how to use a map: clicking, dragging, zooming or tilting are left for them to find), the credits (data sources only: no AI model or tool is credited on anything published), `bounds` the map can be moved within, the terrain `exaggeration`, the tile `sources`, the MapLibre `layers` (colors written as `--map-…` tokens from `maps/map.css`, the site's one palette), `labels` (placed as page text in Source Serif, so the maps need no font files), and named `views`: each a camera (`center`, `zoom`, `pitch`, `bearing`), whether terrain is on, the layers and labels it `show`s, and the still's `alt` and `caption`. Views are framed for a 1200 × 800 map; smaller maps zoom out a little to keep about the same ground in view. The maps carry only David's own layers, with no basemap.

**Tiles.** A map's data is built on the mini by its script, run with QGIS's Python as its header says; it reads the project in Drive without touching it, works in a scratch folder, and writes `vectors.pmtiles` (from the GeoPackage, through GDAL) and `terrain.pmtiles` (Terrarium-encoded elevation in quarter-meter steps, the project's DEM faded into a coarser 3DEP download around it so tilted views have land past the project's edge) into `maps/<name>/`. It needs the `pmtiles` command (Homebrew). Tiles are served from the site; a map whose files outgrow GitHub's limits (100 MB a file) would move them to Cloudflare R2, which no map has needed.

**Stills.** Every view has a still image, `maps/<name>/stills/<view>.jpg`, captured from the map's own page by `node _writing/stills.mjs <name>` (headless Chrome through playwright-core in `~/.local/share/site-stills`). The stills are what a reader sees in email, the feed, print and without JavaScript, and they stay on screen until the live map has drawn; they are captured again whenever a map's data or views change, before `build.py`. A published piece fails to build if a still is missing.

**Writing a map piece.** The piece's frontmatter names its map (`map: <name>`), and David marks passages in plain markdown:

    ::: {.map-step view=contours}
    The passage that goes with this view.
    :::

    ::: {.map-embed view=relief}
    Caption for a map readers can explore.
    :::

Consecutive steps share one map, pinned beside the text on desktop and above it on phones, with an Explore Map / Return to Story button that opens it full screen to pan, zoom and tilt. Each change of view gets its still (linking to its passage) and an anchor, `#view-<name>`. A note at the top, shown only in email and the feed, points readers to the site. The first still is the piece's share image.

**Name:** "David Valerio" is the canonical name. No middle initial.

**Favicon:** the initials DV in Source Serif bold, muted plum (`#5E4B8B`), on a clear background, drawn as outlines inline in `index.html` (source in `_writing/favicon.txt`). `favicon.png` is the same mark as a transparent 64px fallback for Safari, rendered from the drawing with headless Chrome (`--default-background-color=00000000`). `apple-touch-icon.png` keeps the mark on the paper color, because iOS paints transparent areas black.

## Design System

The site follows the Practice Design System, David's house style shared with his documents and utility emails and separate from the Discern Earth brand. Its live version is the Design System artifact of that name (read it fresh when the site's look is in question): Source Serif 4 alone (regular text, semibold name and headings), slate ink (`--ink`), stone gray for the tagline and metadata (`--stone`), barely warm paper (`--paper`), and one muted-plum accent (`--accent`, `#5E4B8B`) on the links, which carry no underline and turn ink on hover. Circular headshot with a hairline border, the one round shape on the site; everything else has square corners. Nothing on the site is set in all caps: metadata lines (kind and date above a piece, the dates in the list) are stone at 0.78rem with 0.02em tracking in normal case, and dates are written `YYYY-MM-DD`.

The writing pages use the same tokens in `writing/style.css`: a 41rem measure and the site's own reading scale (the system's 15px screen scale is sized for emails), a hairline masthead (name left, Writing right), upright stone subtitles (never italic, on the site or in email), and a print stylesheet.

**Light only.** The site, its maps and the workbench have one palette and never follow the device into dark mode (`color-scheme: light` on every page), so a map is designed for one set of colours. Keep every color on a token; `index.html` and `writing/style.css` carry the same values.

## Layout

The first screen (`.card-screen`) is the line drawing as a still image filling the screen from its top edge, with the card set over Williston: a bordered paper panel, centered, holding the portrait, name, tagline and Writing, Maps, Podcasts, Subscribe and Email; Subscribe jumps to the Writing by Email band below the lists. The drawing is centered on Williston, reaching equally far in every direction and west past the Yellowstone's confluence, and it fades into the paper on every side. The image's 150-pixel strip of paper sits above the screen, and the card is sized and placed in the image's own pixels (`--px`) over the city's spot in it (785, 555 of 1600 × 1000), so the card stays on Williston at any window size. The drawing never shows larger than the map's own page shows it (zoom 9.29, `--px` 0.894): on a larger window it stays at that scale, centered in paper. The first screen is always the drawing's full height, so the card never runs into the lists below. The first screen carries no caption; the map's own page names it and its sources. On tall or narrow screens (a phone either way up, a portrait tablet, any window under 900 pixels wide) the whole drawing comes first and the card rises onto its lower edge, and the first screen ends there rather than filling the screen. Below the first screen, one centered column 930 of the drawing's 1600 image pixels wide (in the first screen's `--px`, so it scales with the drawing) holds three lists, one beneath the other, each Writing and Podcasts row a title on the left and its date on the right: Writing (the seven newest essays and papers, the rest behind All Writing), Maps (three maps, each a row with its title and date and its snapshot to the right, the rest behind All Maps) and Podcasts (the seven newest episodes, the rest behind All Podcasts: the Discern Earth conversations, listed by the guest's name and linked to their pages, and David's guest appearances on other shows from `_writing/appearances.yaml`, listed by the show's name and linked to the episode on Apple Podcasts). Beneath each list, its All toggle sits on the left and Back to Top on the right, which returns to the first screen (`#home`). The toggles are plain `<details>`, so the page needs no script; the headings are centered above their lists and carry no counts, and no list labels its items by kind. In the phone layout (portrait, or under 900 pixels wide) the column takes the screen's width. Below them, with no rule between, sits the centered Writing by Email band. To recapture the drawing behind the card, rebuild the Williston Confluence project in Drive and the map's tiles, then capture the four `home/hero-*.jpg` images from the map at the card's view (desktop 1600 × 1000 at twice the pixel density, north up and flat, the drawing below a 150-pixel strip of paper, kept above the screen; tall screens 860 × 600 with the whole drawing), without labels.

## Writing by Email

Readers subscribe with the Writing by Email box, a band below the homepage's three lists and at the foot of every essay, paper and map page (`SUBSCRIBE` in `build.py`; the homepage's copy and its styles are hand-made in `index.html`, kept in step with `writing/style.css`). The form posts to a Cloudflare Worker at subscribe.davalerio.com (`_subscribe/worker.js`), which turns away anything filling the hidden `website` field, caps posts at a few a minute per sender, and allows one confirmation email per address a day (a repeat lands on the same page, sending nothing) and 50 a day in all. It emails a link whose token carries the address and the time encrypted, so the address never shows in the link, and sends the reader to `/subscribe/sent/`. The link works for seven days and opens a Confirm Subscription button, which can be pressed once; only that click adds the address to the Writing segment in Resend and lands on `/subscribe/confirmed/`. Confirming is safe to repeat, so a double click or a dropped request just works the second time; the trade-off, accepted, is that a reader who unsubscribes and then presses Confirm in their own old email within the seven days is subscribed again. Resend's unsubscribe covers the whole account, so the click subscribes again someone who once unsubscribed only when Writing is their only segment; anyone in another segment keeps the opt-out and is told to write to david@. Nothing is added to Resend before the click. The caps live in the Worker's Caps Durable Object, whose calls run one at a time; it holds only fingerprints of addresses, for a day, and a count per day, and the Worker never logs addresses, though the confirmation email itself passes through Resend, which keeps its own logs. The Worker is deployed by hand from `_subscribe/` with `npx wrangler deploy`, under wrangler's own Cloudflare sign-in on the mini (`wrangler login --device`, limited to Workers and read access; run it again if the sign-in lapses); its secrets are `RESEND_API_KEY`, `SEGMENT_ID` and `SIGNING_KEY` (changing `SIGNING_KEY` voids unconfirmed links).

Nothing is emailed on publish. David asks for a piece by its slug or a map page by its name, and the newsletter workflow sends it, run from its Run button on GitHub or with `gh workflow run newsletter.yml -f name=<name> -f to=test`: `to=test` (the default) mails David alone, and only a second run with `to=subscribers` mails the list as a Resend broadcast named `writing:<slug>` or `map:<name>`. An essay or paper goes as its full text, with a map piece's stills linking to their views, the credits once at the end (`offline()` in `build.py`, which the feed uses too); a map page goes as its title, opening still, note, a link to explore it and its credits; conversations are not emailed. Everything is from David Valerio at writing@davalerio.com with replies to david@, ending in Read on davalerio.com · Unsubscribe and a line saying the reader subscribed at davalerio.com (Resend handles unsubscribes; no postal address, by David's choice). The subscriber send runs only in the workflow on main, after a successful test of the same piece on the same commit, and only when the live page is byte for byte the page that commit's source renders, so an unpublished edit, or a source edit never rebuilt, is never mailed. A name Resend lists as already sent never goes again; one Resend shows as stopped partway, in any status but draft, or as a draft from the last ten minutes stops the run for a look in Resend; a failed or uncertain send stops and says so, and is checked in Resend before running again. Until the first broadcast has gone out, every email (tests included) opens with a short note that the Discern Earth newsletter is now Writing by Email, for the 156 subscribers imported from the Ghost export (`2-Writing/_Archive/Ghost Export 2026-09-19/` in Drive); the note drops on its own after that. `send.py <name> --preview` prints the email, without the note. The repo's secrets `RESEND_API_KEY` and `SEGMENT_ID` feed the workflow.
